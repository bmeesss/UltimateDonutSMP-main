# UltimateDonutSmp — Spigot 1.12.2 + Eaglercraft runtime audit

Target platform: **Beast/Spigot 1.12.2 (protocol 335, NMS `v1_12_R1`)**, Java 8 bytecode,
EaglerXServer 1.1.0, ProtocolLib 5.4.0, ViaVersion/ViaBackwards/ViaRewind, LuckPerms 5.5.0,
PlaceholderAPI 2.12.3.

Everything below was traced in source. Where a claim depends on a third-party jar (ProtocolLib)
the exact upstream source is quoted so it can be re-checked.

**Verification method used for this pass:** the repository was parsed and cross-checked against a
real 1.12.2 Bukkit API surface (1005 `org.bukkit` classes, 462 `Material` constants) extracted from
a 1.12.2 server source tree. Checks performed:

* every `Material.*`, `Sound.*`, `Particle.*`, `GameMode.*`, `InventoryType.*`, `Effect.*`,
  `SoundCategory.*`, `DyeColor.*`, `Statistic.*` constant used in `src/main/java` exists in 1.12.2 —
  **0 missing** (146 Material constants, 3 Sound, 8 Particle, 4 GameMode, 3 InventoryType checked);
* every `import org.bukkit.*` resolves to a class present in 1.12.2 — **0 missing** (148 imports);
* every `@EventHandler` parameter type exists in 1.12.2 — **0 missing** (156 handlers);
* every `src/main/java` file parses — **424/424**.

See [1.12.2_VALIDATION.md](1.12.2_VALIDATION.md) for what could **not** be executed here.

## 2. Phase 2 — ProtocolLib entity interaction, in detail

**Question A/B/C: is it ProtocolLib, the plugin, or both?**

**A — ProtocolLib is genuinely incompatible with this 1.12.2 packet mapping.** Not a misuse.
ProtocolLib 5.4.0 `WrappedEnumEntityUseAction` (identical in 5.3.0 and on `master`):

```java
private static final Class<?> PACKET_CLASS = PacketType.Play.Client.USE_ENTITY.getPacketClass();
private static final Class<?>[] DECLARED_CLASSES = PACKET_CLASS.getDeclaredClasses();
private static final ConstructorAccessor INTERACT   = useAction(EnumWrappers.getHandClass());
private static final ConstructorAccessor INTERACT_AT = useAction(EnumWrappers.getHandClass(),
                                                                MinecraftReflection.getVec3DClass());
...
private static ConstructorAccessor useAction(Class<?>... parameterTypes) {
    for (Class<?> subClass : DECLARED_CLASSES) {
        ConstructorAccessor accessor = Accessors.getConstructorAccessorOrNull(subClass, parameterTypes);
        if (accessor != null) return accessor;
    }
    throw new IllegalArgumentException(
        "No constructor with " + Arrays.toString(parameterTypes) + " in " + PACKET_CLASS);
}
```

`1_12_R1 PacketPlayInUseEntity` (protocol 335):

```java
private int a;                                   // target entity id
private PacketPlayInUseEntity.EnumEntityUseAction b;   // INTERACT | ATTACK | INTERACT_AT
private Vec3D c;                                 // only for INTERACT_AT
```

There is no `EnumHand` anywhere in the packet. `DECLARED_CLASSES` has exactly one entry, the plain
enum, which has no constructor at all. `useAction` therefore always throws, and because these are
`static final` fields the class can never initialise on 1.12.2.

The plugin's only mistake was choosing to call it, so **C (both)** in the sense that the plugin must
stop using it — but the wrapper is unfixable from the plugin side.

**Fix shipped (plugin-side, version-safe):** `FakePlayerProtocolLibBridge.isAttackAction` now walks
`packet.getModifier()` and classifies the action field:

| Server | Field layout | Detection |
|---|---|---|
| 1.8 | `int` action | `Number` value `== 1` at field index > 0 |
| 1.9 – 1.16 (incl. 1.12.2) | `EnumEntityUseAction` enum | `Enum#name()` equals `ATTACK` |
| 1.17+ | sealed `ServerboundInteractPacket$Action` | class simple name contains `attack` |

Field 0 is always the entity id, which is why a numeric action is only accepted at a later index —
otherwise an entity id of `1` would be read as an attack.

**ProtocolLib downgrade: not required and not recommended.** The single broken class is avoided
entirely; the rest of the ProtocolLib surface used by this plugin (`EnumWrappers.PlayerInfoAction`,
`NativeGameMode`, `ChatFormatting`, `RenderType`, `DisplaySlot`, `PlayerInfoData`,
`WrappedGameProfile`, `StructureModifier`, `PacketType`) resolves fine on 1.12.2. Downgrading to
ProtocolLib 4.x would additionally break ViaVersion 5.9.1 (which expects the modern ProtocolLib
API) and is a strictly larger risk than not touching one wrapper class.

## 3. Phase 3 — GUI input system

Traced end to end for all four broken inputs. **They are two bugs, not four**, and both live in
`utils/SignInputUtil`:

```
OrdersNewMenu#handleClick(13)  ─┐
OrdersNewMenu#handleClick(14)  ─┤
AuctionHouseBrowseMenu#handleClick(SEARCH) ─┼→ SignInputUtil.openFromConfig(...)
OrdersBrowseMenu#handleClick(search)     ─┘        │
                                                   ├─ Material.SIGN is an ITEM on 1.12.2  → bug #2
                                                   └─ openSign(Sign, Side) is 1.20+       → bug #3
                                                        → catch { finish(player, null) }
                                                        → Consumer<String> called with null
                                                        → menu reopens unchanged, no message
```

There are **no anvil GUIs** in this plugin (`AnvilInventory` appears only in
`AnvilModerationListener`, which moderates real anvils). No conversation API is used. Inventory
click, drag and close handling is ordinary Bukkit and is 1.12.2-safe.

### Shared input mechanism now used

| Transport | When | Java 1.12.2 | Eagler via EaglerXServer |
|---|---|---|---|
| Sign editor | `Player#openSign(Sign, Side)` resolvable (1.20+) | n/a | n/a |
| **Chat input** | every pre-1.20 server, incl. 1.12.2 | works | works — EaglerXServer presents chat as ordinary protocol-47 chat |

Chat input was chosen over an NMS `PacketPlayOutOpenSignEditor` implementation because it needs no
world mutation, no client-side fake block, and no `PacketPlayInUpdateSign` handling — all of which
are the parts that differ between a Java client and an Eagler client. The configured `*_SIGN`
sections still drive the wording: their lines are replayed as the prompt, so `orders.yml`
`SEARCH_SIGN` / `AMOUNT_SIGN` / `PRICE_SIGN` keep working unchanged.

The answer is consumed in `ChatListener#onChat` (`EventPriority.NORMAL`, ahead of the chat
pipeline), so it is never broadcast and never reaches the mute/filter/delay logic. The result is
delivered on the main thread through `SpigotScheduler` using the same `Consumer<String>` callback
the sign transport used, so **no call site changed**.

Defined behaviour:

* empty input → callback `null` (identical to cancelling), menu reopens;
* the word `cancel` → callback `null`, menu reopens;
* 45 s timeout → callback `null` + `SIGN_INPUT.TIMED_OUT` message;
* invalid number → the existing per-field messages (`ORDERS.INVALID_QUANTITY`,
  `ORDERS.QUANTITY_OUT_OF_RANGE`, `ORDERS.INVALID_PRICE`, `ORDERS.PRICE_OUT_OF_RANGE`) — unchanged.

`SignInputUtil.META_SIGN_INPUT` is still set for the whole session, so
`OrdersManager#hasPendingInput` keeps behaving exactly as before.

config-driven icons (menu fillers, buttons) and never for the orders/AH catalogues.

## 5. Phase 11 — config audit

`LegacyMaterialSupport` already covers the pane, wool/terracotta/concrete/carpet/glass/bed/banner/
dye/shulker-box colour families, the wood families, the stone variants, the wood-tool renames and
the straight 1.13 renames. It is now also consulted by `WorthManager` (bug #6).

Remaining known gap, documented rather than rewritten (blind config rewrites are out of scope):

* **`worth.yml` contains several thousand 1.13+ keys** (`TUFF`, `SCULK_*`, `POTTERY_SHERD_*`,
  `ARMOR_TRIM_SMITHING_TEMPLATE`, copper family, …). Most have no 1.12.2 equivalent, so they stay
  unpriced. That is correct behaviour — they are skipped, not converted to `STONE`.
* `amethyst-tools.yml` lists `CHERRY_LOG`, `MANGROVE_LOG`, `CRIMSON_STEM`, `WARPED_STEM`,
  `CRYING_OBSIDIAN`, `ROOTED_DIRT`, `SOUL_SOIL`, `POWDER_SNOW`, `MUD`, `PURPLE_CONCRETE_POWDER`,
  `END_PORTAL_FRAME`, `FARMLAND`. Several of these are post-1.12.2 blocks; they are filtered out of
  the drill/shovel/chopper block lists at load time. No runtime warning is produced — worth adding a
  startup summary if the lists look short in game.

## 6. Not changed, and why

* `checkMinecraftVersionSupport()` requires 1.21.10+ **unless** the version is exactly `1.12.2`,
  which is explicitly whitelisted (`legacySpigot1122`). Verified correct — left alone.
* `PlayerAdvancementDoneEvent` — confirmed present in Spigot-API 1.12.2
  ([javadoc](https://helpch.at/docs/1.12.2/org/bukkit/event/player/PlayerAdvancementDoneEvent.html)).
  Not a problem despite being an "advancement" API.
* `Player.Spigot#sendMessage(ChatMessageType, BaseComponent...)` and `ChatMessageType.ACTION_BAR` —
  both exist in 1.12.2; `PlayerSettingUtils.sendActionBar` is safe.
* `Player#getPing()` is only mentioned in a comment; `PingManager` uses reflection/`EntityPlayer#ping`.
* NETHERITE → DIAMOND mappings, the 62-column `REPLACE INTO players` statement, and the 32/16-char
  scoreboard sanitisation are pre-existing 1.12.2 work and were left intact.
